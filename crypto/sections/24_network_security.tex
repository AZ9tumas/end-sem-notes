\section{Network Security Protocols and System Security}\label{sec:netsec}

The cryptographic tools of the earlier sections (block ciphers and modes, RSA and Diffie--Hellman, hashes, MACs and signatures) become useful only when a protocol fixes exactly which tool protects which bytes, how the keys get there, and in what order the operations are applied. This part of the syllabus studies the standard protocols at three layers of the TCP/IP stack, e-mail security (PGP, S/MIME), IP security (IPSec), web security (SSL/TLS, HTTPS, SET), and then the defence of the computer systems themselves (intruders, malicious software, firewalls, trusted systems). None of it is on this year's slides, so the notes follow Stallings and Forouzan.

\subsection{Where security can be placed in the stack \new}
\likely{``Compare security at the network, transport and application layers'' (3 marks).}

Security can be added at three places, and the choice decides who must change and what is protected.

\textbf{Network level (IPSec).} Security is applied to every IP packet, so it is transparent to applications and to users: no application has to be rewritten, and all traffic between two sites (web, mail, file transfer) is protected at once. \textbf{Transport level (SSL/TLS).} Security sits just above TCP and is used by the applications that ask for it (a browser opening an \ttx{https} connection); it protects one connection at a time. \textbf{Application level (PGP, S/MIME, SET).} Security is built into the application and can be tailored to it: an e-mail is signed by its author and stays signed in the recipient's mailbox, and SET can show the bank the card number while hiding it from the merchant. The price is that every application must implement its own security.

\section{E-mail Security: PGP and S/MIME}\label{sec:email}

\subsection{Why e-mail needs its own security \new}
\likely{``Why can e-mail not use a handshake like TLS?'' (2 marks), as part of a PGP question.}

E-mail is a \textbf{one-way, store-and-forward} service: Alice writes the message, it is passed from server to server, and Bob reads it hours later. Since Alice and Bob are never online together, there is no handshake in which they could agree on algorithms or a session key. Alice must therefore decide everything herself and put it \emph{into} the message: the identifiers of the algorithms, a fresh session key encrypted for Bob, her signature and the information Bob needs to find her public key. Two practical constraints of the mail system shape the design as well: classic SMTP carries only 7-bit ASCII text, so binary ciphertext must be converted to printable characters, and mail servers limit the size of a message. PGP and S/MIME are the two standard solutions; both use the same cryptographic idea (hybrid encryption plus a hash-and-sign signature) and differ mainly in formats and in how public keys are trusted.

\subsection{PGP: the five services \hot\new}
\likely{``Explain the operational description of PGP with a diagram (authentication, confidentiality, both)'' (5--8 marks).}

\textbf{Pretty Good Privacy} (PGP), written by Phil Zimmermann in 1991, is a freely available package that provides confidentiality and authentication for e-mail and file storage. It selected the best available algorithms as building blocks, runs on every platform, and is not controlled by any government or standards body, which explains its spread. PGP offers five services.
\begin{center}\small
\begin{tabularx}{\textwidth}{@{}l l >{\raggedright\arraybackslash}X@{}}
\toprule
Service & Algorithms (classic PGP) & What is done\\
\midrule
Digital signature & DSS/SHA-1 or RSA/SHA-1 & a SHA-1 hash of the message is signed with the sender's private key and attached\\
Message encryption & CAST-128, IDEA or 3DES; session key by RSA or ElGamal & the message is encrypted with a one-time session key, which is encrypted with the recipient's public key and attached\\
Compression & ZIP & the message is compressed for storage and transmission\\
E-mail compatibility & radix-64 conversion & the binary result is converted to printable ASCII\\
Segmentation & --- & long messages are split to fit mail size limits and reassembled\\
\bottomrule
\end{tabularx}
\end{center}

\textbf{Authentication only.} The sender creates the message $M$ and computes its 160-bit SHA-1 hash $H(M)$. The hash is encrypted with RSA under the sender's private key $PR_a$ and prepended to the message. The receiver decrypts the signature with the sender's public key $PU_a$ to recover the hash, computes $H(M)$ of the received message himself, and accepts if the two are equal. Since only Alice holds $PR_a$, a match proves that she created the signature, and since the hash is collision resistant (\S\ref{sec:integrity}), it proves that $M$ was not changed. Signing the hash instead of $M$ keeps the RSA operation short whatever the length of the message.

\textbf{Confidentiality only.} The sender generates a random 128-bit \textbf{session key} $K_s$, used for this message only, and encrypts the message with CAST-128 (or IDEA or 3DES) in 64-bit CFB mode (\S\ref{sec:modes}). The session key is encrypted with RSA under the recipient's public key $PU_b$ and prepended. The receiver recovers $K_s$ with his private key $PR_b$ and decrypts the message. This is \textbf{hybrid encryption}: the slow public-key operation is applied to 128 bits only, the bulk is encrypted by the fast symmetric cipher, and the one-time key removes the need for any earlier key exchange, which a store-and-forward service could not have.

\textbf{Both services.} The sender first signs the plaintext, then encrypts the message together with the signature under $K_s$, and attaches $E(PU_b, K_s)$:
\[
A \to B:\quad E(PU_b, K_s) \,\big\|\, E_{K_s}\!\Big(Z\big(E(PR_a, H(M)) \,\|\, M\big)\Big),
\]
where $Z$ is ZIP compression; the whole result is then radix-64 encoded.

At the receiver the steps run in reverse: radix-64 decoding, recovery of $K_s$ with $PR_b$, symmetric decryption, decompression, and finally verification of the signature with $PU_a$ against a freshly computed $H(M)$.

\subsection{PGP: the order of operations and why \hot\new}
\likely{``Why does PGP sign before compressing and compress before encrypting?'' (3 marks).}

The sender applies the operations in the order \textbf{sign $\to$ compress $\to$ encrypt $\to$ radix-64 $\to$ segment}, and each position has a reason.

\textbf{Sign before compressing.} First, the signature is then computed on the uncompressed message, so the recipient can store the plain message together with the signature and verify it later without keeping a compressed copy or recompressing. Second, PGP's compression is not deterministic: different versions of ZIP trade speed against compression ratio and produce different compressed outputs from the same input. A signature on the compressed form would verify only with the same compressor version; a signature on the original message is independent of the compressor.

\textbf{Compress before encrypting.} Compression removes redundancy, and redundancy is what cryptanalysis feeds on, so encrypting the compressed text strengthens the encryption. It also shortens what has to be encrypted and sent. (Compressing \emph{after} encryption would be useless anyway, since good ciphertext looks random and does not compress.)

\textbf{Radix-64 after encrypting.} The signature, the encrypted session key and the ciphertext are arbitrary binary data, which 7-bit mail systems may corrupt. Radix-64 (the same encoding as MIME base64) maps every 3 bytes to 4 printable characters from a 64-symbol alphabet (A--Z, a--z, 0--9, $+$, $/$), and a 24-bit CRC is appended to detect transmission errors. It expands the data by $4/3$, about 33\%, but ZIP compresses ordinary text by about a factor of 2, so the final message is usually \emph{shorter} than the plaintext: $\frac{1}{2} \times \frac{4}{3} \approx 0.67$.

\textbf{Segmentation last.} Many mail systems limit the message size (e.g.\ 50\,000 bytes), so after all other processing PGP splits a long message into segments that are mailed separately. The session key component and the signature component appear only once, at the start of the first segment; the receiver strips the mail headers and reassembles the whole block before any other processing.

\begin{worked}[: radix-64 and the size of a PGP message]
\textbf{Q.} (a) Radix-64 encode the three bytes \ttx{4D 61 6E} (``Man''). (b) A 60\,000-byte text is signed (signature component 300 bytes), compressed by ZIP with ratio 2, encrypted (CFB, no expansion), given a 260-byte session key component, and radix-64 encoded. Ignoring line breaks and the CRC, how many characters are sent, and how many segments if the mailer accepts at most 20\,000 characters?

\textbf{A.} (a) The 24 bits $01001101\ 01100001\ 01101110$ are regrouped into four 6-bit groups $010011\ 010110\ 000101\ 101110 = 19, 22, 5, 46$. In the radix-64 alphabet (0--25 $\to$ A--Z, 26--51 $\to$ a--z, 52--61 $\to$ 0--9) these are \textbf{T, W, F, u}, so the output is \ttx{TWFu}.\\
(b) Signed: $60\,000 + 300 = 60\,300$ bytes; compressed: $60\,300 / 2 = 30\,150$; with the session key component: $30\,410$ bytes; radix-64: $\lceil 30\,410 / 3 \rceil \times 4 = 10\,137 \times 4 = \mathbf{40\,548}$ \textbf{characters}; segments: $\lceil 40\,548 / 20\,000 \rceil = \mathbf{3}$.\\
\emph{Check}: $40\,548 / 60\,000 = 0.676$, close to the predicted $\frac12 \cdot \frac43 = 0.67$.
\end{worked}

\textbf{Message format.} A PGP message consists of three components. The \emph{message component} holds the data with a filename and a timestamp. The \emph{signature component} holds a timestamp, the \textbf{key ID} of the sender's public key, the \textbf{leading two octets of the message digest} in the clear, and the digest encrypted with the sender's private key. The two clear octets let the receiver check, before doing anything else, that he used the right public key to decrypt the digest: if the decrypted digest does not start with them, the wrong key was used. The \emph{session key component} holds the key ID of the recipient's public key and the encrypted session key. Compression and symmetric encryption cover the signature and message components; radix-64 covers everything.

\subsection{PGP: key IDs and key rings \new}
\likely{``Explain the PGP private-key ring and public-key ring; what is a key ID?'' (4 marks).}

\textbf{Key IDs.} A user may own several key pairs (to change keys from time to time, or to separate work and private use), and he will hold the public keys of many correspondents. The recipient therefore needs to know which public key was used. Sending the whole public key would waste space, so PGP sends a \textbf{key ID}, the least significant 64 bits of the public key: $\text{ID} = PU \bmod 2^{64}$. With 64 bits, the chance that two keys of one user share an ID is negligible.

\textbf{Private-key ring.} Each user stores his own key pairs in a table with one row per pair: timestamp (when the pair was created), key ID, public key, \textbf{encrypted private key}, and user ID (normally the e-mail address); the table can be indexed by user ID or key ID. The private key is never stored in the clear. When a pair is generated, PGP asks for a passphrase, computes its 160-bit SHA-1 hash, and encrypts the private key with CAST-128 using 128 bits of that hash as the key; the passphrase and the hash are then discarded. To sign, the user types the passphrase again, PGP recomputes the hash and decrypts the private key. A thief who copies the ring therefore still needs the passphrase, so the security of the private key rests on the passphrase.

\textbf{Public-key ring.} The public keys of other users are stored with timestamp, key ID, public key, user ID and the three trust fields described next: \textbf{owner trust}, the \textbf{signatures} on the key with their \textbf{signature trust}, and the computed \textbf{key legitimacy}. When a message arrives, PGP uses the key ID in the session key component to fetch the right private key from the private-key ring, and the key ID in the signature component to fetch the sender's public key from the public-key ring.

\subsection{PGP: the web of trust \new}
\likely{``Explain the PGP trust model: owner trust, signature trust, key legitimacy'' (4 marks), with a small example.}

\textbf{Problem.} Public-key encryption is only as safe as the binding between a public key and its owner. If Eve can plant a key with Bob's user ID on Alice's ring, Alice will encrypt to Eve and accept Eve's signatures as Bob's (a man-in-the-middle). PGP has no central certificate authority. Instead, any user may sign another user's public key to vouch that it belongs to that user (a key signature acts as a certificate), and each user decides whom he trusts as an \textbf{introducer}. The resulting graph of mutual signatures is the \textbf{web of trust}.

\textbf{Mechanism.} Each entry of Alice's public-key ring carries three kinds of trust information.
\begin{itemize}
  \item \textbf{Owner trust} says how far Alice trusts the owner of this key to sign \emph{other} people's keys correctly. It is assigned by Alice herself: unknown, usually not trusted, usually (partially) trusted, always (fully) trusted, or ultimate for her own keys.
  \item \textbf{Signature trust} is attached to each signature on the key and is simply a copy of the owner trust of the signer, if the signer is on Alice's ring (otherwise unknown).
  \item \textbf{Key legitimacy} says how far Alice believes the key really belongs to its user ID. PGP computes it from the signature trusts: one signature of ultimate trust makes it complete; otherwise PGP adds weights, $1/X$ for each always-trusted signature and $1/Y$ for each usually-trusted one ($X$ and $Y$ are user parameters, typically $X = 1$, $Y = 2$), and when the sum reaches 1 the key is complete, below 1 it is marginal.
\end{itemize}
The important distinction is that \textbf{legitimacy} concerns the key (is it really Bob's?) while \textbf{owner trust} concerns the person (does Bob check keys carefully before signing them?). A key can be fully legitimate while its owner is not trusted as an introducer. A user revokes a compromised key by issuing a \textbf{key revocation certificate} signed with the corresponding private key and spreading it as widely as possible.

\begin{worked}[: key legitimacy in a web of trust]
\textbf{Q.} Alice gives owner trust \emph{always} to Bob and \emph{usually} to Carol and Dave, and has not assigned any trust to Frank. Weights are 1 for an always-trusted and $\frac12$ for a usually-trusted signer. Determine the legitimacy of the keys of (a) Gita, signed by Bob; (b) Hari, signed by Carol and Dave; (c) Ivan, signed by Carol; (d) Jaya, signed by Frank, whose own key on Alice's ring is legitimate.

\textbf{A.} (a) $1 \ge 1$: \textbf{complete}. (b) $\frac12 + \frac12 = 1$: \textbf{complete}. (c) $\frac12 < 1$: \textbf{marginal}. (d) Frank's owner trust is unknown, so his signature has weight 0: Jaya's key is \textbf{not legitimate}, although Frank's own key is. Legitimacy of the signer's key is not enough; Alice must trust him as an introducer.\\
\emph{Check}: only (a) and (b) reach the threshold 1.
\end{worked}

\subsection{S/MIME and MIME \new}
\likely{``What are the limitations of SMTP/RFC 822 that MIME removes? List the MIME header fields and content types'' (4 marks).}

\textbf{Problem.} The original Internet mail format (RFC 822) and SMTP were designed for short 7-bit ASCII text. As a result, SMTP cannot carry executable files or other binary objects, cannot carry national-language characters (8-bit codes), and may reject messages above a size limit; gateways translating between ASCII and EBCDIC or to X.400 networks use inconsistent mappings; and non-standard SMTP implementations delete or add carriage returns and line feeds, truncate or wrap lines longer than 76 characters, remove trailing white space, pad lines to the same length and convert tabs to spaces. Any of these silently corrupts binary data such as ciphertext or a signature.

\textbf{MIME} (Multipurpose Internet Mail Extensions) solves this within RFC 822 by adding five header fields (MIME-Version, Content-Type, Content-Transfer-Encoding, Content-ID and Content-Description), a set of standard content types, and transfer encodings (7bit, 8bit, binary, quoted-printable for mostly-ASCII text, and \textbf{base64} for arbitrary binary data) that make any content survive the mail system.

\textbf{S/MIME} (Secure/MIME), based on RSA Data Security's technology and standardised by the IETF, adds security to MIME by defining new content types that carry signed and/or encrypted data in the PKCS\#7 (Cryptographic Message Syntax) format. It provides four functions.
\begin{itemize}
  \item \textbf{Enveloped data} (\ttx{application/pkcs7-mime; smime-type=envelopedData}): the sender generates a random session key, encrypts the content with it (3DES or AES), and for \emph{each} recipient encrypts the session key with that recipient's public RSA key and builds a RecipientInfo block (recipient's certificate identifier, algorithm identifier, encrypted session key). The RecipientInfo blocks and the encrypted content are then base64 encoded. This gives confidentiality, and one message serves many recipients with one bulk encryption.
  \item \textbf{Signed data} (\ttx{smime-type=signedData}): the sender hashes the content (SHA), encrypts the digest with his private key, and builds a SignerInfo block (signer's certificate, digest and signature algorithm identifiers, encrypted digest). Content and signature are base64 encoded \emph{together}, so only an S/MIME-capable reader can see the content.
  \item \textbf{Clear-signed data} (\ttx{multipart/signed}): the signature is computed the same way, but the message has two parts: the content in its normal MIME form, readable by anyone, and a detached signature (\ttx{application/pkcs7-signature}) in base64. Recipients without S/MIME can still read the message, though they cannot verify it.
  \item \textbf{Signed and enveloped data}: the two operations can be nested in either order, signing the plaintext and then enveloping it, or enveloping and then signing the ciphertext.
\end{itemize}

\textbf{Certificates.} S/MIME uses \textbf{X.509 version 3} certificates issued by certification authorities. Its key management is a hybrid of a strict CA hierarchy and PGP's web of trust: each client is configured with a list of trusted root certificates and certificate revocation lists, and a user agent must generate key pairs, request certificates from a CA, and store and retrieve certificates of its correspondents.

\section{IP Security (IPSec)}\label{sec:ipsec}

\subsection{Why security at the IP level; applications and services \new}
\likely{``What are the applications and benefits of IPSec? List the services provided by AH and ESP'' (4 marks).}

\textbf{Problem.} IP itself offers no security: the source address of a packet can be forged, and any router or eavesdropper on the path can read or change the contents. Securing each application separately (as PGP does for mail) leaves all other traffic unprotected. \textbf{IPSec} adds authentication, integrity and confidentiality to IP itself, so that every packet between two hosts or two networks can be protected whatever application produced it. It is optional in IPv4 and was designed together with IPv6.

\textbf{Applications.} IPSec is used for secure branch-office connectivity over the Internet (a \textbf{virtual private network}, VPN, instead of leased lines), secure remote access for employees through an ISP, extranet and intranet connections with partners, and as a basis for electronic commerce, since all traffic between the sites is protected without changes to the applications.

\textbf{Benefits.} When IPSec is implemented in a firewall or router, it protects all traffic crossing the perimeter, while traffic inside the site carries no security overhead; and if all outside traffic must use IP through the firewall, IPSec there cannot be bypassed. Because it lies below the transport layer, it is \textbf{transparent to applications and to end users}: no software on the hosts has to change and users need no training or keys. It can also protect individual users where needed, and it secures routing (router advertisements and redirects really come from authorised routers).

\textbf{Architecture and services.} IPSec consists of two traffic protocols, the \textbf{Authentication Header} (AH), which authenticates packets, and the \textbf{Encapsulating Security Payload} (ESP), which encrypts and optionally authenticates them, plus a key-management protocol (IKE) and the documents that define the algorithms. Together they provide the following services.

\subsection{Security associations, SAD and SPD \hot\new}
\likely{``What is a security association? What parameters identify it? Explain SAD and SPD'' (4 marks).}

\textbf{Idea.} Before two parties can protect packets they must agree on the protocol (AH or ESP), the algorithms, the keys, the lifetime and so on. IPSec stores such an agreement as a \textbf{security association} (SA): \imp{a one-way relationship between a sender and a receiver that affords security services to the traffic carried on it.} Since it is one-way, a two-way conversation needs two SAs, one in each direction, and an SA covers one protocol only, AH or ESP. An SA is uniquely identified by three parameters:
\begin{itemize}
  \item the \textbf{Security Parameters Index} (SPI), a 32-bit value chosen by the receiver and carried in every AH and ESP header, which lets the receiver select the SA for an arriving packet;
  \item the \textbf{IP destination address}, the address of the SA's endpoint (an end host or a firewall/router);
  \item the \textbf{security protocol identifier}, which says whether the SA is AH or ESP.
\end{itemize}

\textbf{Security Association Database (SAD).} Each IPSec host keeps one entry per SA with the parameters needed to process its packets: the sequence number counter and its overflow flag, the anti-replay window, the AH information (authentication algorithm and keys), the ESP information (encryption and authentication algorithms, keys, IVs), the lifetime of the SA, the IPSec mode (transport or tunnel) and the path MTU.

\textbf{Security Policy Database (SPD).} The SPD decides \emph{which} traffic gets \emph{which} protection. Each entry is defined by \textbf{selectors}, values of IP and upper-layer fields (destination and source IP addresses, user ID, data sensitivity level, transport protocol, source and destination ports), and specifies an action: \textbf{discard} the packet, \textbf{bypass} IPSec, or \textbf{protect} it with the SA(s) the entry points to. For every outbound packet IPSec compares the packet's fields with the SPD, finds the matching entry, determines the SA (creating one with IKE if none exists yet) and applies its processing. For an inbound packet the receiver uses the SPI, destination address and protocol to find the SA in the SAD, processes the packet, and then checks that the result is allowed by the SPD.

\subsection{Transport mode and tunnel mode \hot\new}
\likely{``Differentiate transport and tunnel mode; draw the packet formats for AH and ESP in both modes'' (5 marks).}

Both AH and ESP can be used in two modes, which differ in what is protected and in where the IPSec processing is done.

\textbf{Transport mode} protects the \emph{payload} of the IP packet, i.e.\ the upper-layer segment (TCP or UDP header plus data). The AH or ESP header is inserted between the original IP header and the payload, and the original IP header stays visible. It is used for \textbf{end-to-end} communication between two hosts that both run IPSec, such as a client and a server.

\textbf{Tunnel mode} protects the \emph{entire} original IP packet. After the AH or ESP fields are added, the whole packet (including its original header) becomes the payload of a \textbf{new outer IP packet} with a new header, normally addressed from one security gateway to another. Routers on the path see only the outer header, so the inner source and destination addresses are hidden. Tunnel mode is used when one or both ends of the SA are \textbf{security gateways} (firewalls or routers): hosts behind the gateways need no IPSec at all, and the gateways build a VPN between the sites.

\subsection{Authentication Header (AH) \hot\new}
\likely{``Draw the AH format and explain each field; which IP header fields are authenticated?'' (4--5 marks).}

\textbf{Purpose.} AH provides data integrity and data origin authentication of IP packets, plus anti-replay protection. It prevents address spoofing, since the source address is authenticated, and it stops replay through the sequence number. It is based on a MAC (HMAC, \S\ref{sec:integrity}), so the two parties must share a secret key. AH provides \emph{no} confidentiality.

\textbf{Fields.}
\begin{itemize}
  \item \textbf{Next header} (8 bits) identifies the header that follows AH (e.g.\ TCP in transport mode, IP in tunnel mode).
  \item \textbf{Payload length} (8 bits) is the length of AH in 32-bit words, minus 2.
  \item \textbf{Reserved} (16 bits) for future use.
  \item \textbf{SPI} (32 bits) identifies the SA.
  \item \textbf{Sequence number} (32 bits) is a monotonically increasing counter used for anti-replay.
  \item \textbf{Authentication data} (variable, a multiple of 32 bits) holds the \textbf{integrity check value} (ICV), a MAC of the packet; the defaults were HMAC-MD5-96 and HMAC-SHA-1-96, i.e.\ the HMAC truncated to its first 96 bits.
\end{itemize}

\textbf{What the ICV covers.} The MAC must be the same at the sender and at the receiver, but some IP header fields legitimately change on the way. AH therefore computes the MAC over the IP header fields that are \textbf{immutable} in transit (version, header length, total length, identification, protocol, source address, destination address) or \textbf{mutable but predictable} at the endpoint (the destination address when source routing is used, which is set to its final value). The \textbf{mutable, unpredictable} fields (type of service, flags, fragment offset, time to live, header checksum) are set to zero for the calculation at both ends. The MAC also covers the AH header itself, with the authentication data field set to zero, and the entire upper-layer data, which is immutable. Because the source and destination addresses are inside the MAC, an attacker cannot change them without detection; this is also why AH does not work through NAT, which rewrites addresses.

\begin{worked}[: AH length field and packet size]
\textbf{Q.} AH uses HMAC-SHA-1-96. Find the value of the Payload length field and the size of the packet when a 37-byte TCP segment (20-byte header, 17 data bytes) is sent from a host with a 20-byte IPv4 header in transport mode and in tunnel mode.

\textbf{A.} Fixed AH fields: $1 + 1 + 2 + 4 + 4 = 12$ bytes; ICV $= 96$ bits $= 12$ bytes; AH $= 24$ bytes $= 6$ words, so Payload length $= 6 - 2 = \mathbf{4}$.\\
Transport: $20 + 24 + 37 = \mathbf{81}$ bytes. Tunnel: new IP header $+$ AH $+$ inner packet $= 20 + 24 + (20 + 37) = \mathbf{101}$ bytes.\\
\emph{Check}: tunnel mode costs exactly one extra 20-byte IP header.
\end{worked}

\subsection{Anti-replay service \new}
\likely{``Explain the IPSec anti-replay window with an example'' (3--4 marks).}

\textbf{Problem.} In a replay attack the attacker records an authenticated packet and sends it again later; the MAC is still valid, so authentication alone cannot reject it. IP gives no ordering guarantee, so the receiver also cannot simply demand increasing numbers: packets may legitimately arrive out of order.

\textbf{Sender side.} When an SA is created, the sender's sequence counter is set to 0; for each packet it is incremented and written into the Sequence number field, so the first packet carries 1. The counter must not wrap around past $2^{32} - 1$: before that the SA is terminated and a new SA with a new key is negotiated, so no number repeats under one key.

\textbf{Receiver side.} The receiver keeps a \textbf{window} of size $W$ (default 64) whose right edge $N$ is the highest sequence number received so far in a valid packet; for each number from $N - W + 1$ to $N$ it remembers whether a valid packet with that number has arrived (marked slot). For an arriving packet:
\begin{enumerate}
  \item if its number is \textbf{inside the window} and the slot is unmarked, the MAC is checked; if it is valid, the slot is marked;
  \item if its number is \textbf{to the right of the window}, the MAC is checked; if it is valid, the window is advanced so that this number becomes the right edge, and its slot is marked;
  \item if its number is \textbf{to the left of the window}, or the slot is already marked, or the MAC fails, the packet is discarded (and the event is logged).
\end{enumerate}
The MAC is checked before the window moves, so a forged packet with a huge sequence number cannot push the window forward.

\subsection{Encapsulating Security Payload (ESP) \hot\new}
\likely{``Draw the ESP format; why is padding needed? Compare AH and ESP'' (5 marks).}

\textbf{Purpose.} ESP provides \textbf{confidentiality} (encryption of the payload), limited traffic-flow confidentiality, and optionally the same authentication, integrity and anti-replay services as AH, all with one header and trailer (format above).

\textbf{Fields.} \textbf{SPI} and \textbf{sequence number} are as in AH. \textbf{Payload data} (variable) is the transport-layer segment (transport mode) or the whole inner IP packet (tunnel mode), encrypted; if the cipher needs an IV (e.g.\ AES-CBC, \S\ref{sec:modes}), it is carried in the clear at the start of this field. \textbf{Padding} (0--255 bytes) is followed by the \textbf{pad length} (8 bits, the number of padding bytes) and the \textbf{next header} (8 bits, the type of the encrypted payload). \textbf{Authentication data} (variable) is the ICV, computed over the ESP packet from the SPI to the next-header field, i.e.\ \emph{after} encryption.

\textbf{Why padding.} Padding is added for three reasons: a block cipher needs the plaintext (payload, padding, pad length and next header) to be a whole number of blocks; ESP requires the pad-length and next-header fields to end on a 32-bit boundary, so the ciphertext is a multiple of 4 bytes; and extra padding can hide the true length of the payload, which gives partial traffic-flow confidentiality.

\textbf{Encrypt-then-MAC.} Because the ICV is computed over the ciphertext, the receiver checks it first and discards bogus or replayed packets \emph{before} spending time on decryption, which reduces the impact of denial-of-service attacks, and the two operations can be done in parallel. Unlike AH, ESP's authentication does \emph{not} cover the IP header in front of the ESP header (in tunnel mode the inner header is covered, being inside the payload).

\begin{worked}[: ESP padding and packet size]
\textbf{Q.} ESP uses AES-CBC (16-byte blocks, 16-byte explicit IV) and HMAC-SHA-1-96 (12-byte ICV). The same 37-byte TCP segment as above is sent. Find the padding and the total packet size in transport and in tunnel mode (IPv4 header 20 bytes).

\textbf{A.} The encrypted part is payload $+$ padding $+$ pad length (1) $+$ next header (1), a multiple of 16.\\
Transport: payload $= 37$; $37 + 2 = 39$; padding $= (-39) \bmod 16 = \mathbf{9}$; encrypted part $= 48$ bytes. Total $= 20$ (IP) $+ 8$ (SPI, seq.) $+ 16$ (IV) $+ 48 + 12$ (ICV) $= \mathbf{104}$ bytes.\\
Tunnel: payload $=$ inner packet $= 20 + 37 = 57$; $57 + 2 = 59$; padding $= (-59) \bmod 16 = \mathbf{5}$; encrypted part $= 64$. Total $= 20 + 8 + 16 + 64 + 12 = \mathbf{120}$ bytes.\\
\emph{Check}: $48 = 3 \times 16$ and $64 = 4 \times 16$.
\end{worked}

\subsection{Combining security associations \new}
\likely{``Explain transport adjacency and iterated tunnelling; give the basic combinations of SAs'' (4 marks).}

One SA implements either AH or ESP, but not both, and a packet may need different services between different pairs of nodes (end-to-end authentication between hosts, plus encryption between the two gateways). IPSec therefore allows a packet to be processed by a sequence of SAs, called an \textbf{SA bundle}. SAs are combined in two ways. In \textbf{transport adjacency} more than one security protocol is applied to the same IP packet without tunnelling, for example ESP and then AH in transport mode between the same two hosts; since both act at the same endpoints, only one level of combination is possible. In \textbf{iterated tunnelling} several layers of protocols are applied by IP tunnelling, one inside the other; each tunnel may start and end at a different IPSec node along the path, so many levels of nesting are possible.

\textbf{Authentication plus confidentiality} can be obtained in three ways: ESP with its authentication option; transport adjacency with an inner ESP SA (no authentication) and an outer AH SA, which has the advantage that the authentication now also covers the IP addresses; or a bundle of an inner AH transport SA and an outer ESP tunnel SA, which authenticates the plaintext before encryption, so the authentication data are protected by encryption and can be stored with the message for later checking.

\textbf{Basic combinations} (Stallings). Case 1: end-to-end security between two IPSec hosts (AH or ESP in transport mode, or one inside the other). Case 2: security only between two gateways, a simple VPN with one tunnel SA, the hosts doing nothing. Case 3: case 2 plus case 1, a gateway-to-gateway tunnel that carries end-to-end transport SAs between the hosts. Case 4: a remote host reaches the organisation's firewall over the Internet with a tunnel SA, and an inner SA protects the traffic all the way to the server inside.

\subsection{Key management: Oakley, ISAKMP and IKE \hot\new}
\likely{``How does Oakley improve Diffie--Hellman? Explain cookies (clogging attack) and nonces (replay)'' (5 marks).}

\textbf{Problem.} AH and ESP need shared secret keys: two pairs per two-way SA bundle (one for integrity, one for encryption in each direction). With \textbf{manual} key management an administrator configures each system with its own and its peers' keys, which only works for small static networks. \textbf{Automated} management creates keys on demand; the default for IPSec is \textbf{ISAKMP/Oakley}, later called the Internet Key Exchange (\textbf{IKE}). Oakley is a key-determination protocol based on Diffie--Hellman (\S\ref{sec:keymgmt}); ISAKMP is the framework that defines the message formats and procedures for negotiating, establishing, modifying and deleting SAs.

\textbf{Weaknesses of plain Diffie--Hellman.} Diffie--Hellman lets two parties create a shared secret $g^{xy} \bmod p$ over a public channel, but (1) it provides no information about the identities of the parties, so a man in the middle can run one exchange with each side (\S\ref{sec:keymgmt}); and (2) it is computationally intensive, which opens a \textbf{clogging attack}: the attacker sends a flood of requests with forged source addresses, each forcing the victim to compute a modular exponentiation, until its processor is exhausted.

\textbf{Oakley's improvements.} Oakley keeps the advantages of Diffie--Hellman (keys are created only when needed, no pre-existing infrastructure beyond global parameters) and adds five features:
\begin{itemize}
  \item \textbf{Cookies} to thwart clogging attacks.
  \item Negotiation of a \textbf{group}, i.e.\ the global parameters of the exchange (768- or 1024-bit modular exponentiation, or elliptic-curve groups).
  \item \textbf{Nonces} to ensure against replay attacks.
  \item Exchange of the Diffie--Hellman public values.
  \item \textbf{Authentication} of the exchange, by digital signatures, public-key encryption or a symmetric key, to thwart man-in-the-middle attacks.
\end{itemize}

\textbf{Cookies.} Each side sends a pseudorandom number, the cookie, in its first message, and the other side must echo it in the first message of the Diffie--Hellman exchange. A cookie is sent to the claimed source address, so an attacker who forges the address never receives it and cannot echo it. As a result \imp{the attacker can only make the victim generate cookies, never perform the expensive exponentiation.} A cookie must satisfy three requirements: it must depend on the specific parties (so that a cookie obtained with the attacker's real address cannot be reused from forged addresses and ports); it must be impossible for anyone but the issuer to generate a cookie the issuer will accept (so it depends on a local secret, which cannot be deduced from any cookie); and generating and checking it must be fast. The recommended construction is a fast hash over the source and destination IP addresses, the source and destination ports and a locally generated secret value, $\mathrm{CKY} = H(\mathrm{IP}_s \| \mathrm{IP}_d \| \mathrm{port}_s \| \mathrm{port}_d \| \text{secret})$; the issuer stores nothing and simply recomputes the hash when the cookie comes back.

\textbf{The aggressive Oakley exchange} (Stallings) above uses three messages. CKY are cookies, OK\_KEYX marks a key-exchange message, GRP names the Diffie--Hellman group, $g^x$ and $g^y$ are the public values, EHAO and EHAS are the encryption, hash and authentication algorithms offered and selected, NIDP says that the rest of the message is not encrypted, ID are identities, $N$ are nonces, and $S_K[\,\cdot\,]$ is a signature with the sender's private key.
\begin{itemize}
  \item \textbf{Message 1.} I sends its cookie, the group and its public value $g^x$, the algorithms it offers, both identities and a fresh nonce $N_I$, and signs the identities, nonce, group, $g^x$ and offer with its private key. The signature binds $g^x$ to I's identity, so a man in the middle cannot substitute his own value.
  \item \textbf{Message 2.} R returns its cookie and echoes I's, sends $g^y$, the selected algorithms and its nonce $N_R$, echoes $N_I$, and signs all of this \emph{including} $N_I$ and $g^x$. Signing I's fresh nonce proves that the reply is new and not a replay, and signing $g^x$ confirms which exchange it answers.
  \item \textbf{Message 3.} I echoes R's cookie, which proves that I really receives messages at its claimed address, and signs both nonces and both public values, which proves to R that I is live and holds the private key.
\end{itemize}
Both sides then compute $K = g^{xy} \bmod p$ and derive the keys from it. The aggressive mode saves messages but makes R compute $g^y$ before it has seen its own cookie echoed; the six-message \textbf{main mode} first exchanges cookies and the SA proposal (messages 1--2), then the Diffie--Hellman values and nonces (3--4), and only then the identities and authentication, encrypted under the new key (5--6), which also hides the identities from eavesdroppers.

\textbf{ISAKMP and the IKE phases.} An ISAKMP message starts with a header holding the initiator and responder cookies (64 bits each), the type of the next payload, version numbers, the exchange type, flags, a message ID and the length, followed by a chain of payloads (SA, proposal, transform, key exchange, identification, certificate, certificate request, hash, signature, nonce, notification, delete). IKE works in two phases. \textbf{Phase 1} (main or aggressive mode) authenticates the peers and builds a protected \textbf{IKE SA} between them. \textbf{Phase 2} (``quick mode'') runs under the protection of the IKE SA and quickly negotiates the actual AH/ESP SAs, and can be repeated to create more SAs or to rekey without a new Diffie--Hellman exchange. The current version, IKEv2, does the same with four messages (IKE\_SA\_INIT and IKE\_AUTH) and lets a busy responder answer the first message statelessly with a cookie, the same anti-clogging idea.

\section{Web Security: SSL/TLS, HTTPS and SET}\label{sec:tls}

\subsection{Web security threats and the SSL/TLS architecture \hot\new}
\likely{``Explain the SSL architecture (protocol stack); differentiate an SSL session and an SSL connection'' (4 marks).}

\textbf{Problem.} The web is a client/server application over the Internet: anyone can publish a server, users are often unskilled, and web servers are complex and a doorway into an organisation's systems. The threats are to \emph{integrity} (modification of user data or messages in transit), \emph{confidentiality} (eavesdropping on the network, theft of data from the server or client), \emph{authentication} (impersonation of legitimate users or servers, forged data) and \emph{availability} (denial of service). Encryption, MACs and certificates answer the first three; denial of service is hard to prevent by cryptography.

\textbf{Secure Sockets Layer} (SSL, Netscape; version 3.0 in 1996) and its IETF successor \textbf{Transport Layer Security} (TLS 1.0, 1999, essentially SSL 3.1) provide a secure channel on top of TCP. SSL is not one protocol but two layers of protocols:
\begin{center}
\begin{tikzpicture}[font=\footnotesize]
\tikzset{sl/.style={draw, minimum height=0.5cm, inner sep=1pt, anchor=west}}
\node[sl, minimum width=2.2cm, fill=gold!20] at (0,1.0) {Handshake};
\node[sl, minimum width=2.6cm, fill=gold!20] at (2.2,1.0) {Change Cipher Spec};

\node[sl, minimum width=2.3cm] at (6.4,1.0) {HTTP (FTP, \dots)};

\node[sl, minimum width=8.7cm] at (0,0) {TCP};
\node[sl, minimum width=8.7cm] at (0,-0.5) {IP};
\end{tikzpicture}
\end{center}
The \textbf{Record Protocol} provides confidentiality and integrity to whatever higher-layer data it carries, in particular HTTP. Three higher-layer protocols manage the channel: the \textbf{Handshake Protocol} authenticates the parties and negotiates algorithms and keys, the \textbf{Change Cipher Spec Protocol} switches to the newly negotiated parameters, and the \textbf{Alert Protocol} reports errors and closure.

\textbf{Session and connection.} An SSL \textbf{connection} is a transport (in the OSI sense) that provides a suitable type of service; connections are peer-to-peer, transient, and each is associated with one session. An SSL \textbf{session} is an association between a client and a server created by the Handshake Protocol; it defines a set of cryptographic security parameters that can be shared among \emph{multiple connections}. Sessions exist to avoid the expensive negotiation of new parameters for every connection: a browser that opens ten connections to a site runs the full public-key handshake once and resumes the session for the others. The \emph{session state} holds the session identifier, the peer's X.509 certificate, the compression method, the cipher spec (bulk encryption and MAC algorithms), the 48-byte \textbf{master secret} and an ``is resumable'' flag. The \emph{connection state} holds the server and client randoms, the server and client write MAC secrets, the server and client write keys, the IVs and the sequence numbers; each direction has its own keys.

\subsection{The Record Protocol \hot\new}
\likely{``Explain the operation of the SSL Record Protocol with a diagram'' (4 marks).}

The Record Protocol takes an application message and processes it in five steps.

\begin{enumerate}
  \item \textbf{Fragmentation.} The message is split into blocks of at most $2^{14} = 16\,384$ bytes.
  \item \textbf{Compression} (optional, lossless). It must not increase the length by more than 1024 bytes; in practice it is not used.
  \item \textbf{MAC.} A MAC is computed over the (compressed) fragment with the shared MAC write secret. In SSLv3 it is a precursor of HMAC, $\mathrm{hash}(K \| \mathrm{pad}_2 \| \mathrm{hash}(K \| \mathrm{pad}_1 \| \mathrm{seq\_num} \| \mathrm{type} \| \mathrm{length} \| \mathrm{fragment}))$; TLS uses true HMAC over $\mathrm{seq\_num} \| \mathrm{type} \| \mathrm{version} \| \mathrm{length} \| \mathrm{fragment}$. The 64-bit \textbf{sequence number} is not transmitted; both sides count records, so a deleted, reordered or replayed record makes the MAC fail.
  \item \textbf{Encryption.} The fragment and MAC are encrypted with the write key, using a block cipher in CBC mode (DES, 3DES, IDEA, AES; \S\ref{sec:modes}) with padding, or a stream cipher (RC4). Encryption may add at most 1024 bytes, so a record body is at most $2^{14} + 2048$ bytes.
  \item \textbf{Header.} A 5-byte header is prepended: \textbf{content type} (8 bits: change\_cipher\_spec, alert, handshake or application\_data), \textbf{major and minor version} (8 bits each; 3.0 for SSLv3, 3.1 for TLS 1.0) and the \textbf{length} of the record body in bytes (16 bits).
\end{enumerate}
The receiver decrypts, verifies the MAC, decompresses and reassembles before delivering the data to the application. SSL/TLS up to version 1.2 is \textbf{MAC-then-encrypt}, the opposite of IPSec ESP; this order later enabled padding-oracle attacks on CBC (Lucky 13, POODLE) and is one reason TLS 1.3 abandoned it.

\subsection{Change Cipher Spec and Alert protocols \new}
\likely{``What is the purpose of the Change Cipher Spec and Alert protocols?'' (2 marks).}

The \textbf{Change Cipher Spec Protocol} is the simplest of the three: it consists of a single message of one byte with value 1. Its effect is to copy the \emph{pending} state, negotiated during the handshake, into the \emph{current} state, so that all following records use the new cipher suite and keys. Each direction switches separately, when its sender sends this message.

The \textbf{Alert Protocol} conveys SSL-related alerts to the peer. Each alert message has two bytes: a \textbf{level}, warning (1) or fatal (2), and a \textbf{code}. Fatal alerts (unexpected\_message, bad\_record\_mac, decompression\_failure, handshake\_failure, illegal\_parameter) make SSL terminate the connection immediately; other connections of the same session may continue, but no new connections may be opened on the session. Warnings include close\_notify (the sender will send no more data; each side must send it before closing the write side, which detects truncation attacks), no\_certificate, bad\_certificate, unsupported\_certificate, certificate\_revoked, certificate\_expired and certificate\_unknown.

\subsection{The Handshake Protocol \hot\new}
\likely{``Draw and explain the SSL/TLS handshake in four phases'' (6--8 marks).}

\textbf{Problem.} Before any data are protected, the client and server must agree on a protocol version and a cipher suite, the server (and optionally the client) must be authenticated, and both must end up with the same fresh secret keys, all over a channel that the attacker controls. The Handshake Protocol does this in four phases; each message has a 1-byte type, a 3-byte length and the content.

Messages marked * are optional or depend on the key-exchange method (dashed).

\textbf{Phase 1: establish security capabilities.} The client sends \textbf{client\_hello} with: the highest SSL/TLS \textbf{version} it understands; a \textbf{random} of 32 bytes (a 4-byte timestamp and 28 bytes from a secure generator), which serves as a nonce against replay; a \textbf{session ID} (zero for a new session, nonzero to resume an existing one); the \textbf{cipher suite} list in decreasing order of preference, each entry naming a key-exchange method (RSA, fixed Diffie--Hellman, ephemeral Diffie--Hellman, anonymous Diffie--Hellman, Fortezza) and a cipher spec (bulk cipher, MAC algorithm, cipher type, hash size, key material, IV size); and the compression methods it supports. The server replies with \textbf{server\_hello}: the lower of the two highest versions, its own independent random, the session ID, and the \emph{one} cipher suite and compression method it selected from the client's lists.

\textbf{Phase 2: server authentication and key exchange.} The server sends its \textbf{certificate} (an X.509 chain), required for every method except anonymous Diffie--Hellman. It sends \textbf{server\_key\_exchange} only when the certificate does not already contain what the client needs: for anonymous or ephemeral Diffie--Hellman (the server's $p$, $g$ and $g^y \bmod p$) or when the server's RSA key is for signing only. These parameters are \textbf{signed} by the server over $\mathrm{hash}(\text{ClientHello.random} \| \text{ServerHello.random} \| \text{ServerParams})$; including both randoms ties the signature to this handshake, so an old signed message cannot be replayed. A server that wants client authentication sends \textbf{certificate\_request} (acceptable certificate types and CAs). Finally \textbf{server\_hello\_done}, which is always sent, says that the server's part of the hello is complete, and the server waits.

\textbf{Phase 3: client authentication and key exchange.} The client checks that the server's certificate is valid (signature chain, dates, host name) and that the server's parameters are acceptable. If a certificate was requested, it sends its \textbf{certificate} (or a no\_certificate alert). It then sends \textbf{client\_key\_exchange}, which is mandatory: with RSA, the client generates a 48-byte \textbf{pre-master secret} and sends it encrypted under the server's public key; with ephemeral or anonymous Diffie--Hellman it sends its public value $g^x \bmod p$; with fixed Diffie--Hellman the value is in its certificate and the message is empty. If the client sent a certificate with signing capability, it also sends \textbf{certificate\_verify}, a signature over a hash of all preceding handshake messages and the master secret. This proves that the client owns the private key of its certificate: anyone could send a copy of the certificate, but only the owner can sign the transcript.

\textbf{Phase 4: finish.} The client sends \textbf{change\_cipher\_spec} (through the Change Cipher Spec Protocol, not the handshake) and copies the pending cipher spec into the current one, then immediately sends \textbf{finished} under the new algorithms and keys. Finished contains a keyed hash of the master secret and the whole handshake transcript; in TLS 1.0/1.1
\[
\text{verify\_data} = \mathrm{PRF}\big(\text{master\_secret}, \text{``client finished''}, \mathrm{MD5}(\text{handshake\_msgs}) \,\|\, \mathrm{SHA\text{-}1}(\text{handshake\_msgs})\big)[0..11].
\]
The server does the same: its own change\_cipher\_spec and finished. Since each side checks the other's Finished against its own view of the transcript, \textbf{any tampering with the earlier, unprotected handshake messages is detected}, for example an attacker who deleted the strong cipher suites from client\_hello to force a weak one (a downgrade attack). After Phase 4 the client and server exchange application data.

\subsection{Master secret and key derivation \new}
\likely{``How are the master secret and the session keys generated in SSL/TLS?'' (3--4 marks).}

The keys are created in two stages. First a \textbf{pre-master secret} is shared: with RSA the client generates it and sends it encrypted under the server's public key; with Diffie--Hellman both sides compute $g^{xy} \bmod p$. Then both sides compute the 48-byte \textbf{master secret} from it and the two randoms. In SSLv3,
\[
\begin{aligned}
\text{master\_secret} = {}& \mathrm{MD5}(\text{pre\_master} \| \mathrm{SHA}(\text{`A'} \| \text{pre\_master} \| \text{ClientHello.random} \| \text{ServerHello.random})) \;\|\\
& \mathrm{MD5}(\text{pre\_master} \| \mathrm{SHA}(\text{`BB'} \| \text{pre\_master} \| \text{ClientHello.random} \| \text{ServerHello.random})) \;\|\\
& \mathrm{MD5}(\text{pre\_master} \| \mathrm{SHA}(\text{`CCC'} \| \text{pre\_master} \| \text{ClientHello.random} \| \text{ServerHello.random})),
\end{aligned}
\]
three 16-byte MD5 outputs. TLS replaces this by a \textbf{pseudorandom function} built from HMAC:
\[
\text{master\_secret} = \mathrm{PRF}(\text{pre\_master\_secret}, \text{``master secret''}, \text{ClientHello.random} \| \text{ServerHello.random})[0..47],
\]
\[
P\_\mathrm{hash}(\text{secret}, \text{seed}) = \mathrm{HMAC}(\text{secret}, A(1) \| \text{seed}) \,\|\, \mathrm{HMAC}(\text{secret}, A(2) \| \text{seed}) \,\|\, \cdots,
\]
\[
A(0) = \text{seed}, \qquad A(i) = \mathrm{HMAC}(\text{secret}, A(i-1)),
\]
which expands a short secret into as many bytes as needed (TLS 1.0/1.1 XOR a P\_MD5 and a P\_SHA-1 stream computed on the two halves of the secret; TLS 1.2 uses P\_SHA-256). Finally the master secret is expanded into the \textbf{key block}, $\mathrm{PRF}(\text{master\_secret}, \text{``key expansion''}, \text{ServerHello.random} \| \text{ClientHello.random})$, which is cut into the client and server write MAC secrets, the client and server write keys, and the client and server IVs.

\textbf{Why both randoms.} The master secret depends on both parties' fresh randoms, so neither side alone controls the keys, and every session has new keys even if a pre-master secret were reused. In particular, an attacker who replays a recorded client\_key\_exchange to the server gets nowhere: the server has chosen a new random, so the replay leads to a different master secret and fails at the Finished check.

\begin{worked}[: size of the TLS key block]
\textbf{Q.} A TLS 1.0 session uses the cipher suite TLS\_RSA\_WITH\_AES\_128\_CBC\_SHA. How many bytes of key block must the PRF produce, and how many iterations of P\_SHA-1 and P\_MD5 does that need?

\textbf{A.} MAC secrets: HMAC-SHA-1, 20 bytes each, $2 \times 20 = 40$. Write keys: AES-128, 16 bytes each, $2 \times 16 = 32$. IVs: one AES block each, $2 \times 16 = 32$. Key block $= 40 + 32 + 32 = \mathbf{104}$ \textbf{bytes}. P\_SHA-1 gives 20 bytes per iteration: $\lceil 104/20 \rceil = \mathbf{6}$; P\_MD5 gives 16: $\lceil 104/16 \rceil = \mathbf{7}$; both streams are truncated to 104 bytes and XORed.\\
\emph{Check}: for TLS\_RSA\_WITH\_3DES\_EDE\_CBC\_SHA the block is $2 \times 20 + 2 \times 24 + 2 \times 8 = 104$ bytes as well (24-byte 3DES keys, 8-byte IVs).
\end{worked}

\subsection{From SSL to TLS 1.3 \new}
\likely{``What are the differences between SSL and TLS?'' / ``What did TLS 1.3 change?'' (3 marks).}

\textbf{TLS 1.0--1.2 versus SSLv3.} The version number is 3.1--3.3; the MAC is standard HMAC with the version in its input; keys come from the HMAC-based PRF instead of SSL's ad hoc MD5/SHA construction; there are more alert codes; Fortezza is dropped from the cipher suites; the certificate\_verify and finished computations use the PRF; and the padding before encryption may be any amount up to 255 bytes (to hide message lengths) instead of the minimum.

\textbf{TLS 1.3} (RFC 8446, 2018) is a redesign. It removes RSA key transport and static Diffie--Hellman, keeping only ephemeral (EC)DHE, so that every session has \textbf{forward secrecy} (stealing the server's private key later does not decrypt recorded sessions). It removes compression, CBC MAC-then-encrypt and RC4, allowing only AEAD ciphers (AES-GCM, ChaCha20-Poly1305). The handshake takes one round trip: the client sends its key share in client\_hello, and everything after server\_hello, including the server certificate, is encrypted. Keys are derived with HKDF, renegotiation is gone, Change Cipher Spec survives only as a dummy for middlebox compatibility, and a resumed session can send data in its first flight (0-RTT), at the cost of possible replay of that data.

\subsection{HTTPS \new}
\likely{``What is HTTPS? Which parts of an HTTP exchange are protected?'' (2 marks).}

\textbf{HTTPS} is HTTP over SSL/TLS. The URL begins with \ttx{https://} and the server listens on port \textbf{443} instead of 80. When HTTPS is used, the URL of the requested document, the document contents, the contents of browser forms, the cookies sent in both directions and the contents of the HTTP headers are all encrypted; only the server's IP address and port (and, in older TLS, the host name in the certificate) are visible. The client opens a TCP connection, runs the TLS handshake, and only then sends the first HTTP request. The browser checks that the server's certificate is valid and issued for the host name in the URL; this check is what stops a man in the middle, who can present a certificate only for his own name. At the end, each side sends a TLS close\_notify alert before closing the TCP connection, so that an attacker who forges a TCP close cannot silently truncate a page.

\subsection{SET: purpose and participants \new}\label{sec:set}
\likely{``What is SET? List its participants and requirements'' (4 marks).}

\textbf{Secure Electronic Transaction} (SET), specified by MasterCard and Visa in 1996, is an open encryption and security specification for protecting \textbf{credit card transactions} on the Internet. It is not a payment system itself but a set of security protocols and formats that lets users use the existing card payment infrastructure securely over an open network. SET provides a secure channel among all parties, trust through X.509v3 certificates, and \textbf{privacy}, because information is available to a party only when and where it is needed. Its business requirements are: confidentiality of payment and ordering information; integrity of all transmitted data; authentication that the cardholder is a legitimate user of the card account; authentication that the merchant can accept card payments through a relationship with a financial institution; use of the best security practices; and independence from transport-level security and interoperability across platforms. Confidentiality used DES, integrity RSA signatures with SHA-1, and authentication X.509v3 certificates.

\textbf{Participants.}
\begin{itemize}
  \item The \textbf{cardholder}, an authorised holder of a payment card issued by an issuer, who buys over the Internet.
  \item The \textbf{merchant}, who sells goods or services and must have a relationship with an acquirer to accept cards.
  \item The \textbf{issuer}, the financial institution (bank) that issued the card and is responsible for the cardholder's payments.
  \item The \textbf{acquirer}, the financial institution that keeps the merchant's account, authorises card transactions (the card is valid and the purchase within the limit) and transfers payments to the merchant's account; it is later reimbursed by the issuer over the payment network.
  \item The \textbf{payment gateway}, operated by the acquirer or a third party, which processes the merchant's SET payment messages and interfaces between SET on the Internet and the existing bank-card networks.
  \item The \textbf{certification authority} (CA), trusted to issue X.509v3 certificates to cardholders, merchants and payment gateways, in a hierarchy of CAs.
\end{itemize}

\textbf{Sequence of events.} (1) The customer opens a card account and (2) receives a certificate signed by the bank, which binds his RSA public key to the card. (3) Merchants have two certificates, one for signing and one for key exchange, and hold a copy of the payment gateway's certificate. (4) The customer places an order. (5) The merchant sends a copy of its certificate, so the customer can verify that it is a valid store. (6) The customer sends the order and the payment information together with his certificate; the payment information is encrypted so that the merchant cannot read it. (7) The merchant forwards the payment information to the payment gateway and requests authorisation. (8) The merchant confirms the order to the customer, (9) provides the goods or service, and (10) later requests payment from the gateway, which handles all payment processing.

\subsection{SET: the dual signature \hot\new}
\likely{``What is a dual signature? How is it constructed and how do the merchant and the bank verify it?'' (5 marks).}

\textbf{Problem.} A purchase involves two messages for two recipients: the \textbf{order information} (OI), meant for the merchant, and the \textbf{payment information} (PI, the card details), meant for the bank. The merchant does not need the card number, and the bank does not need to know what was bought, so each should see only its own message. Yet the two must be \textbf{linked}: the customer needs to be able to prove that this payment is for this order and no other. If the customer signed OI and PI separately, a dishonest merchant could take the signed PI from one order and claim it pays for a different, more expensive order.

\textbf{Construction.} The customer hashes each message separately, hashes the concatenation of the two digests, and signs that:
\[
\mathrm{PIMD} = H(\mathrm{PI}), \qquad \mathrm{OIMD} = H(\mathrm{OI}), \qquad \mathrm{POMD} = H(\mathrm{PIMD} \,\|\, \mathrm{OIMD}), \qquad \mathrm{DS} = E(PR_c, \mathrm{POMD}),
\]
where $H$ is SHA-1, $PR_c$ is the customer's private signature key, and DS is the \textbf{dual signature}.
\begin{center}
\begin{tikzpicture}[font=\footnotesize]
\node[nsL] (pi) at (0,0.65) {PI};
\node[nsL] (oi) at (0,-0.65) {OI};
\node[nsB] (h1) at (1.1,0.65) {$H$};
\node[nsB] (h2) at (1.1,-0.65) {$H$};
\node[nsC] (cc) at (3.4,0) {$\|$};
\node[nsB] (h3) at (4.5,0) {$H$};
\node[nsB] (e) at (6.6,0) {$E$};
\node[nsL] (pr) at (6.6,0.9) {$PR_c$};
\node[nsL, fill=gold!25, draw] (ds) at (8.1,0) {DS};
\draw[nsA] (pi) -- (h1); \draw[nsA] (oi) -- (h2);
\draw[nsA] (h1) -| node[above, pos=0.3]{PIMD} (cc); \draw[nsA] (h2) -| node[below, pos=0.3]{OIMD} (cc);
\draw[nsA] (cc) -- (h3); \draw[nsA] (h3) -- node[above]{POMD} (e); \draw[nsA] (pr) -- (e); \draw[nsA] (e) -- (ds);
\end{tikzpicture}
\end{center}

\textbf{Verification by the merchant.} The merchant receives OI, PIMD (not PI) and DS, and has the customer's public key $PU_c$ from his certificate. He computes
\[
H\big(\mathrm{PIMD} \,\|\, H(\mathrm{OI})\big) \quad\text{and}\quad D(PU_c, \mathrm{DS}),
\]
and accepts if they are equal. The second value is POMD as signed by the customer. The first equals POMD exactly when the OI he received is the one the customer hashed, because $H(\mathrm{OI}) = \mathrm{OIMD}$; PIMD is used as received, so the merchant never needs PI.

\textbf{Verification by the bank.} The bank (through the payment gateway) receives PI, OIMD (not OI) and DS, and computes
\[
H\big(H(\mathrm{PI}) \,\|\, \mathrm{OIMD}\big) \quad\text{and}\quad D(PU_c, \mathrm{DS}),
\]
which are equal exactly when the PI is the one the customer signed, so the bank never needs OI.

\textbf{Why the link holds.} Both checks compare against the same signed value POMD, which depends on both PIMD and OIMD. If the merchant presented the payment with a different order OI$'$, the bank and a judge would compute $H(\mathrm{PIMD} \| H(\mathrm{OI}'))$, and since $H$ is collision resistant this differs from POMD, so the signature does not match. Only the customer, holding $PR_c$, can produce a DS for a new pair. Thus \imp{the dual signature lets each party verify its own message while seeing only the digest of the other, and binds the order and the payment together.}

\begin{worked}[: a toy dual signature]
\textbf{Q.} Let the hash be the toy function $H(x) = (7x + 3) \bmod 101$, let the concatenation of two digests $a \| b$ be the number $1000a + b$, and let the customer's RSA key be $n = 187$, $e = 7$, $d = 23$ (\S\ref{sec:rsa}). For $\mathrm{PI} = 2345$ and $\mathrm{OI} = 678$, compute the dual signature and show both verifications.

\textbf{A.} $\mathrm{PIMD} = (7 \cdot 2345 + 3) \bmod 101 = 16\,418 \bmod 101 = 56$. $\mathrm{OIMD} = (7 \cdot 678 + 3) \bmod 101 = 4749 \bmod 101 = 2$.\\
$\mathrm{PIMD} \| \mathrm{OIMD} = 56\,002$; $\mathrm{POMD} = (7 \cdot 56\,002 + 3) \bmod 101 = 392\,017 \bmod 101 = 36$.\\
$\mathrm{DS} = 36^{23} \bmod 187 = \mathbf{60}$.\\
Merchant (has OI, PIMD $= 56$, DS): $H(678) = 2$, $H(56\,002) = 36$; $60^{7} \bmod 187 = 36$. Equal: accepted.\\
Bank (has PI, OIMD $= 2$, DS): $H(2345) = 56$, $H(56\,002) = 36$; $60^7 \bmod 187 = 36$. Equal: accepted.\\
\emph{Check}: a changed order $\mathrm{OI}' = 679$ gives $H(679) = 9$ and $H(56\,009) = 85 \ne 36$, so the substitution is detected.
\end{worked}

\textbf{Initiate request and response.} After browsing and choosing, the cardholder asks the merchant for the certificates of the merchant and of the payment gateway. The merchant answers with a message signed with its private signature key that contains a transaction ID and both certificates. The cardholder verifies the certificates through their CA signatures and creates OI and PI, each containing the transaction ID.

\textbf{Purchase request.} The cardholder generates a one-time symmetric key $K_s$ and sends
\[
\underbrace{E_{K_s}(\mathrm{PI} \,\|\, \mathrm{DS} \,\|\, \mathrm{OIMD}) \,\|\, E(PU_{g}, K_s)}_{\text{digital envelope, forwarded to the gateway}} \;\|\; \underbrace{\mathrm{PIMD} \,\|\, \mathrm{OI} \,\|\, \mathrm{DS}}_{\text{for the merchant}} \;\|\; \mathrm{Cert}_c ,
\]
where $PU_g$ is the gateway's key-exchange public key. The merchant cannot open the envelope, so he never sees the card details. He verifies the cardholder's certificate and the dual signature as above, processes the order, forwards the envelope to the gateway, and returns a signed \textbf{purchase response} with the transaction ID.

\textbf{Payment authorisation.} The merchant's \textbf{authorisation request} to the gateway contains the cardholder's envelope, an authorisation block with the transaction ID signed with the merchant's private key and encrypted under a new one-time key (in its own digital envelope for the gateway), and the certificates. The gateway verifies all certificates, opens both envelopes, verifies the merchant's signature and the \textbf{dual signature}, checks that the transaction ID in the merchant's block matches the one in PI, and obtains authorisation from the issuer over the bank network. It returns a signed \textbf{authorisation response} with a capture token. Later the merchant sends a \textbf{capture request} with the token to obtain the money.

\textbf{Advantages and disadvantages.} SET gave strong privacy (the merchant never learns the card number, the bank never learns the order) and strong authentication of all parties by certificates. It failed in practice because every cardholder needed software and a certificate, and the many public-key operations made it slow and expensive. Card payments today use TLS between browser and merchant plus issuer-side checks (3-D Secure) and tokenisation, but the dual-signature idea remains the standard example of linking two messages for different recipients.

\section{System Security: Intruders, Malicious Software, Firewalls and Trusted Systems}\label{sec:syssec}

\subsection{Intruders \new}
\likely{``Classify intruders; list intrusion techniques'' (3 marks).}

The protocols above protect data on the wire; the remaining threats attack the computer systems themselves. One of the two most publicised threats is the \textbf{intruder}, a hacker or cracker who gains, or tries to gain, unauthorised access (the other is malicious software). Anderson's classification has three classes.
\begin{itemize}
  \item A \textbf{masquerader} is an individual who is not authorised to use the computer and who penetrates the system's access controls to exploit a legitimate user's account. Masqueraders are usually outsiders.
  \item A \textbf{misfeasor} is a legitimate user who accesses data, programs or resources for which he is not authorised, or who is authorised but misuses his privileges. Misfeasors are usually insiders.
  \item A \textbf{clandestine user} is an individual who seizes supervisory (administrator) control of the system and uses it to evade auditing and access controls or to suppress audit collection. He may be an outsider or an insider.
\end{itemize}
\textbf{Intrusion techniques.} The intruder's goal is to gain access to a system or to increase his privileges, and the information he needs most is a password. The system protects its password file either by a one-way function (only hashed passwords are stored) or by access control. The intruder therefore tries default passwords shipped with the system, all short passwords, words from dictionaries and lists of likely passwords, and personal data of the users (names, birthdays, phone numbers, car numbers); he also installs a Trojan horse that captures passwords, or taps the line between a remote user and the host.

\subsection{Intrusion detection \new}
\likely{``Differentiate statistical anomaly detection and rule-based detection; what is a honeypot?'' (4 marks).}

\textbf{Idea.} Prevention eventually fails, so a second line of defence watches for intruders. Intrusion detection is motivated by three facts: an intruder detected quickly can be ejected before he does damage; an effective detection system deters intrusions; and it collects information about intrusion techniques that strengthens prevention. It rests on the assumption that the behaviour of an intruder differs from that of a legitimate user in ways that can be quantified. The two behaviour profiles overlap, however, so every detector trades \textbf{false positives} (legitimate users flagged as intruders) against \textbf{false negatives} (intruders missed): a looser threshold catches more intruders and annoys more users.

\textbf{Approaches.} \textbf{Statistical anomaly detection} collects data on the behaviour of legitimate users over a period of time and applies statistical tests to observed behaviour to decide with high confidence whether it is legitimate. It has two forms: \emph{threshold detection}, which sets user-independent thresholds on the frequency of events (e.g.\ failed logins per minute), and \emph{profile-based} detection, which builds a profile of each user's activity (login times, programs used, CPU and I/O usage) and detects changes in it, using counters, gauges, interval timers and tests such as mean and standard deviation, multivariate correlation and Markov models. \textbf{Rule-based detection} defines a set of rules that decide whether a given behaviour is that of an intruder: \emph{anomaly} rules are derived from past usage patterns, and \emph{penetration identification} is an expert system that searches for known suspicious sequences (attack signatures). Statistical detection is effective against \textbf{masqueraders}, who are unlikely to imitate the behaviour of the accounts they steal, but not against misfeasors, who act within their normal profile; rule-based penetration identification catches misfeasors and known attacks, since it recognises the events themselves.

\textbf{Audit records.} Detection runs on audit records of user activity. \emph{Native} audit records come from the operating system's accounting software, so no extra software is needed, but they may lack the needed information; \emph{detection-specific} records are generated for the detector alone, which makes them vendor-independent at the cost of running two accounting packages. Denning's record has six fields: \textbf{subject} (initiator of the action), \textbf{action} (login, read, execute, \dots), \textbf{object} (file, program, device), \textbf{exception condition} (any error raised), \textbf{resource usage} (CPU time, lines printed, records read) and \textbf{time-stamp}. For example, the command \ttx{COPY GAME.EXE TO <Library>GAME.EXE} issued by Smith produces records such as (Smith, execute, \ttx{<Library>COPY.EXE}, 0, CPU $= 00002$, 11058721678) and (Smith, write, \ttx{<Library>GAME.EXE}, write-violation, RECORDS $= 0$, 11058721679).

\textbf{Honeypots.} A \textbf{honeypot} is a decoy system designed to lure a potential attacker away from critical systems. It is filled with fabricated information that looks valuable but that no legitimate user would ever access, so \emph{any} access to it is suspect, and it is instrumented with monitors and event loggers. It diverts the attacker, collects information about his activity, and encourages him to stay long enough for the administrators to respond.

\subsection{Password management \new}
\likely{``Explain the UNIX password scheme with salt; why is the salt used?'' (4 marks), possibly with a cost calculation.}

\textbf{The UNIX scheme.} Each user selects a password of up to eight printable characters, which is converted into a 56-bit value (7-bit ASCII) and used as the \emph{key} of an encryption routine. The routine, \ttx{crypt(3)}, is DES modified by a 12-bit \textbf{salt}, which in older systems is derived from the time the password was assigned; it encrypts a 64-bit block of zeros, feeds the output back as input, and repeats 25 times. The 64-bit result is translated into an 11-character string, and the password file stores, for each user ID, this hashed password together with a \emph{plaintext copy} of the salt. At login the user gives his ID and password; the system uses the ID to find the salt and the stored hash, runs crypt on the typed password with that salt, and compares the result with the stored value.

\textbf{Why the salt.} The salt serves three purposes. It prevents duplicate passwords from being visible in the password file: two users with the same password almost certainly get different salts and hence different hashes. It effectively lengthens the password without the user remembering more: each password has $2^{12} = 4096$ possible hashed forms, so a precomputed dictionary must be 4096 times larger. And the modified DES defeats off-the-shelf DES hardware for brute-force guessing. Since the hash is one-way, the scheme does not need to keep the file secret, but in practice the hashes are moved to a \textbf{shadow password file} readable only by the system, and modern systems use salted, deliberately slow hashes (bcrypt, PBKDF2, scrypt, Argon2) because a stolen file can be attacked offline.

\textbf{Password selection strategies.} Users choose guessable passwords, so four strategies are used: \emph{user education} (often ignored); \emph{computer-generated} passwords (random, hence hard to remember and likely to be written down); \emph{reactive checking}, in which the system periodically runs its own password cracker and cancels the passwords it guesses (costly, and weak passwords stay vulnerable until found); and \textbf{proactive checking}, in which the system checks a password at the moment it is chosen against rules (length, character mix) and a dictionary of bad passwords, rejecting weak ones while still letting the user choose a memorable password.

\begin{worked}[: what the salt costs the attacker]
\textbf{Q.} An attacker has a stolen UNIX password file with 1000 users, all with different salts, and a dictionary of $2^{20}$ candidate passwords. Compare the number of crypt evaluations needed to test the dictionary against every user (a) if there were no salt, (b) with 12-bit salts; and (c) the size of a table that precomputes the dictionary for every salt.

\textbf{A.} (a) Without salt one pass of $2^{20}$ hashes, each compared with all 1000 stored hashes, tests every user at once: $\mathbf{2^{20}} \approx 10^6$ evaluations.\\
(b) With salt each user's hashes must be computed with his own salt: $1000 \times 2^{20} \approx \mathbf{1.05 \times 10^{9}}$ evaluations, 1000 times more.\\
(c) $2^{20} \times 2^{12} = \mathbf{2^{32}} \approx 4.3 \times 10^{9}$ entries, 4096 times the size of the plain dictionary.\\
\emph{Check}: the salt does not make any single password harder to guess ($2^{20}$ per user); it removes the attacker's ability to share work across users.
\end{worked}

\subsection{Malicious software: taxonomy \hot\new}
\likely{``Define virus, worm, Trojan horse, logic bomb, trapdoor, zombie'' / ``Differentiate virus and worm'' (4--5 marks).}

\textbf{Malicious software} (malware) is software designed to damage or misuse a system. Stallings divides it into programs that \textbf{need a host program} (they are fragments that cannot exist independently: trapdoors, logic bombs, Trojan horses, viruses) and \textbf{independent} programs that the operating system can schedule and run (worms, zombies), and, across that, into programs that \textbf{replicate} (viruses, worms) and those that do not.

\subsection{Viruses: phases, structure and types \hot\new}
\likely{``Explain the phases of a virus and the types of viruses'' (5 marks).}

\textbf{Phases.} During its lifetime a typical virus goes through four phases.
\begin{itemize}
  \item \textbf{Dormant phase}: the virus is idle and will eventually be activated by some event, such as a date, the presence of another program or file, or the disk exceeding some capacity. Not all viruses have this phase.
  \item \textbf{Propagation phase}: the virus places an identical copy of itself into other programs or into certain system areas on the disk. Each infected program now contains a clone of the virus, which will itself enter a propagation phase.
  \item \textbf{Triggering phase}: the virus is activated to perform the function for which it was intended, caused by a system event, which can include the count of how many times this copy has replicated itself.
  \item \textbf{Execution phase}: the function is performed. It may be harmless (a message on the screen) or damaging (destruction of programs and data files).
\end{itemize}

\textbf{Structure.} A virus can be prepended or appended to an executable program, or embedded in it some other way. The key is that when the infected program is invoked, the virus code runs first and the original program runs afterwards, so the user notices nothing.
\begin{keybox}[title=Structure of a simple virus (Stallings)]
\footnotesize
\begin{verbatim}
program V :=
{goto main;
  1234567;
  subroutine infect-executable :=
    {loop: file := get-random-executable-file;
     if (first-line-of-file = 1234567) then goto loop
     else prepend V to file; }
  subroutine do-damage := {whatever damage is to be done}
  subroutine trigger-pulled := {return true if some condition holds}
main: main-program :=
    {infect-executable;
     if trigger-pulled then do-damage;
     goto next;}
next:
}
\end{verbatim}
\end{keybox}
The marker \ttx{1234567} lets the virus recognise programs it has already infected, so that it does not infect them twice. Such a virus is easy to detect because an infected program is longer than the original; a \emph{compression virus} therefore compresses the host program so that the infected version has the same length.

\textbf{Types.}
\begin{itemize}
  \item A \textbf{parasitic virus}, the traditional and most common form, attaches itself to executable files and replicates by finding other executables to infect whenever an infected program runs.
  \item A \textbf{memory-resident virus} lodges in main memory as part of a resident system program and from then on infects every program that executes.
  \item A \textbf{boot sector virus} infects the master boot record or boot record and spreads when the system is booted from the disk containing it.
  \item A \textbf{stealth virus} is designed to hide itself from antivirus software, for example by compression or by intercepting disk I/O so that a read of an infected area returns the original, uninfected program.
  \item A \textbf{polymorphic virus} mutates with every infection, making detection by a fixed ``signature'' impossible. It creates functionally equivalent copies with different bit patterns, by inserting superfluous instructions or reordering independent ones, or more effectively by \emph{encryption}: a mutation engine encrypts the body of the virus with a fresh random key at each infection and stores the key and a small decryption routine with it; only that routine stays visible, and it is itself varied.
  \item A \textbf{metamorphic virus} also mutates with every infection, but rewrites itself completely each time, possibly changing its behaviour as well as its appearance.
  \item A \textbf{macro virus} is written in the macro language of an application such as Word or Excel and infects documents rather than executable code. It is particularly threatening because it is platform-independent, documents are shared far more often than programs, it spreads easily by e-mail, and file-system access controls are of little use since users are expected to modify documents.
  \item An \textbf{e-mail virus} (Melissa, 1999) arrives as an attachment, typically a macro, and when it is opened sends itself to everyone in the user's address book, so it spreads in hours instead of months.
\end{itemize}

\subsection{Worms, bots and ransomware \new}
\likely{``How does a worm propagate? Give an example'' (3 marks).}

A \textbf{worm} actively seeks out more machines to infect, and each infected machine serves as a launching pad for further attacks. To replicate it uses a network vehicle: the \textbf{e-mail} facility (mailing a copy of itself), a \textbf{remote execution} capability (running a copy on another system), or a \textbf{remote login} capability (logging in to a remote system and copying itself there). It has the same four phases as a virus; in its propagation phase it searches for other systems to infect (by examining host tables or address books), establishes a connection with a remote system, and copies itself there and causes the copy to run, often by exploiting a software vulnerability so that no user action is needed. The \textbf{Morris worm} (1988) exploited UNIX \ttx{finger}, \ttx{sendmail} and password guessing; \textbf{Code Red} (2001) and \textbf{SQL Slammer} (2003) infected hundreds of thousands of servers within hours by scanning random addresses.

\textbf{Bots} (zombies) wait for commands from a controller over a command-and-control channel, and a \textbf{botnet} of thousands of them is used for distributed denial-of-service attacks, spam and click fraud; the attacks come from innocent machines, which makes them hard to trace. \textbf{Ransomware} turns cryptography against the victim: the malware generates a symmetric key, encrypts the user's files (AES), and encrypts that key under the attacker's RSA \emph{public} key, which is embedded in the malware. Only the attacker's private key can recover the file key, so neither analysing the malware nor the victim's machine helps; WannaCry (2017) combined this with a worm that spread through a Windows file-sharing vulnerability. The defences are offline backups and prompt patching.

\subsection{Virus countermeasures \new}
\likely{``Explain the generations of antivirus software; what is generic decryption?'' (3--4 marks).}

The ideal solution is \textbf{prevention}, by not allowing a virus into the system, but in general this is impossible, so antivirus software aims at \textbf{detection} (determine that an infection has occurred), \textbf{identification} (determine which virus it is) and \textbf{removal} (remove all traces and restore the program to its original state); if removal fails, the infected program is discarded and a clean backup reloaded. Stallings identifies four generations of antivirus software.
\begin{itemize}
  \item \textbf{First generation: simple scanners} require a virus signature (the virus's fixed structure and bit pattern) to identify it, so they are limited to known viruses; others merely record program lengths and look for changes.
  \item \textbf{Second generation: heuristic scanners} use heuristic rules to search for probable infection, such as code fragments typical of viruses (e.g.\ the start of a decryption loop of a polymorphic virus), and \textbf{integrity checking}: a checksum of each program is stored and recomputed. A plain checksum or hash can be recomputed by a virus that changes the program, so the check uses a \emph{keyed} hash (a MAC, \S\ref{sec:integrity}) whose key is kept away from the programs.
  \item \textbf{Third generation: activity traps} are memory-resident programs that identify a virus by its \emph{actions} rather than its structure, so no signature is needed.
  \item \textbf{Fourth generation: full-featured protection} packages combine scanning, activity traps and access control, which limits the ability of a virus to penetrate the system and to update files.
\end{itemize}
\textbf{Generic decryption} (GD) catches polymorphic viruses: the suspect file is run in a \textbf{CPU emulator}, a software computer under the control of an \textbf{emulation control module}, while a \textbf{virus signature scanner} watches the emulated memory. A polymorphic virus must decrypt its body to run, so after enough emulated instructions the plaintext virus appears in memory and is recognised, without risk to the real machine. \textbf{Behaviour-blocking software} integrates with the operating system and monitors programs in real time for malicious actions (opening, deleting or modifying files, formatting disks, changing executables or system settings, initiating network connections), blocking them before they take effect. IBM's \textbf{digital immune system} adds automation: a suspicious program on one client is sent to a central virus-analysis machine, which runs it safely, derives a prescription (signature and removal), and distributes it to all clients.

\subsection{Firewalls: design goals and control techniques \hot\new}
\likely{``What are the design goals of a firewall? List the four control techniques'' (4 marks).}

\textbf{Problem.} An organisation with hundreds of hosts on the Internet cannot secure every one of them individually: each runs different software with different flaws. A \textbf{firewall} is inserted between the premises network and the Internet to establish a controlled link and an outer security wall or perimeter, so that security is enforced at a single choke point. Bellovin and Cheswick give three design goals.
\begin{enumerate}
  \item \textbf{All traffic} from inside to outside, and vice versa, must pass through the firewall; this is achieved by physically blocking all access to the local network except via the firewall.
  \item \textbf{Only authorised traffic}, as defined by the local security policy, is allowed to pass.
  \item The firewall itself is \textbf{immune to penetration}, which implies a trusted system with a secure operating system.
\end{enumerate}
\textbf{Control techniques.} \textbf{Service control} decides which types of Internet services can be accessed, inbound or outbound (by IP address and port number, by proxy software, or by hosting the service on the firewall). \textbf{Direction control} decides in which direction particular service requests may be initiated and allowed to flow. \textbf{User control} controls access to a service according to which user is attempting it, usually for local users, and for remote users with secure authentication such as IPSec. \textbf{Behaviour control} controls how particular services are used, e.g.\ filtering spam out of e-mail or giving external users access to only part of the web server.

\textbf{Capabilities.} The single choke point keeps unauthorised users out, prohibits vulnerable services from entering or leaving, and protects against IP spoofing and routing attacks; it gives one location for monitoring, audits and alarms; it is a convenient platform for functions such as network address translation and usage logging; and it can serve as the endpoint of IPSec tunnels for a VPN.

\subsection{Types of firewall \hot\new}
\likely{``Explain packet filter, stateful inspection, application-level and circuit-level gateways; design a packet-filter rule set'' (5--8 marks).}

\textbf{Packet-filtering router.} A packet filter applies a set of rules to each incoming and outgoing IP packet and then forwards or discards it. The rules match fields of the packet: source and destination IP address, source and destination port (which identifies the application, e.g.\ 25 for SMTP, 80 for HTTP), the IP protocol field, TCP flags, and the router interface the packet arrived on or leaves by. The rules are checked in order and the first match decides; if no rule matches, a \textbf{default policy} applies. \emph{Default discard} (that which is not expressly permitted is prohibited) is the conservative choice: everything is blocked at first and services are added case by case. \emph{Default forward} (that which is not expressly prohibited is permitted) is easier for users but means the administrator must react to each new threat.

\begin{center}\small\setlength{\tabcolsep}{4pt}
\begin{tabular}{@{}c l l l l l l l l@{}}
\toprule
\# & Dir & Source address & Src port & Dest.\ address & Dst port & Flag & Action & Purpose\\
\midrule
1 & in & 192.168.1.0/24 & * & * & * & & deny & spoofed inside address from outside\\
2 & in & * & $>1023$ & 192.168.1.10 & 80, 443 & & allow & requests to our web server\\
3 & out & 192.168.1.10 & 80, 443 & * & $>1023$ & ACK & allow & web server's replies\\

5 & out & 192.168.1.20 & 25 & * & * & ACK & allow & SMTP server's replies\\

\bottomrule
\end{tabular}

The \textbf{ACK flag} in rules 3, 5 and 7 is essential. The first packet of a TCP connection (SYN) has no ACK, and every later packet has it, so a rule that requires ACK only admits packets of connections that were opened from the other side. Without it, rule 7 would let an outsider open a connection to \emph{any} high port inside, simply by sending from source port 80. Rule 1 is anti-spoofing: a packet arriving from the Internet cannot legitimately carry an inside source address.

\textbf{Advantages and disadvantages.} Packet filters are simple, transparent to users and very fast. But they do not examine upper-layer data, so they cannot block application-specific attacks or commands; their logging is limited; most do not support user authentication; they are open to attacks on TCP/IP itself; and rule sets are easy to get wrong. Three attacks and their countermeasures are standard. In \textbf{IP address spoofing}, an outsider sends packets with an internal source address; the filter discards packets with an inside source address that arrive on the external interface (rule 1). In a \textbf{source routing attack} the sender specifies the route, hoping to bypass checks; the filter discards all packets that use the source-route option. In a \textbf{tiny fragment attack} the intruder fragments a packet so finely that the TCP header falls into a second fragment, which escapes rules that test TCP fields; the filter requires the first fragment to contain a minimum amount of the transport header, and if it rejects the first fragment it remembers the packet and discards all later fragments.

\textbf{Stateful inspection firewall.} A client normally uses a port number above 1023 for its side of a TCP connection, so a simple packet filter must admit inbound traffic to all high-numbered ports (rule 7), a large hole. A stateful inspection firewall tightens this by keeping a \textbf{directory (state table) of outbound TCP connections}, one entry per established connection (source and destination addresses and ports, connection state), and admits inbound packets to high ports only if they fit an entry in the directory. Some also track TCP sequence numbers to stop session hijacking.

\textbf{Application-level gateway} (proxy server). The gateway relays application-level traffic. The user contacts it with an application such as Telnet or FTP, the gateway asks for the remote host and for authentication, and then opens its own connection to the remote application and relays the application data between the two connections. If the gateway has no proxy code for an application, that service is simply not available, and each proxy can be restricted to the commands the administrator considers acceptable. \emph{Advantages}: it is more secure than a packet filter, since it only has to scrutinise a few allowed applications instead of all combinations at TCP/IP level, and it can log and audit all traffic at application level. \emph{Disadvantage}: the extra processing on every connection, since the gateway splices two connections and examines all traffic in both directions.

\textbf{Circuit-level gateway.} The gateway does not permit an end-to-end TCP connection either; it sets up two TCP connections, one with the inside host and one with the outside host, but once both exist it relays TCP segments \emph{without examining their contents}. Its security function is deciding which connections are allowed. A typical use is with trusted inside users: application-level proxies for inbound connections and circuit-level relaying for outbound ones, which avoids the processing overhead of examining outgoing data. SOCKS is the standard circuit-level gateway.

\subsection{Bastion host and firewall configurations \hot\new}
\likely{``Explain screened host and screened subnet firewall configurations with diagrams; what is a bastion host / DMZ?'' (5 marks).}

A \textbf{bastion host} is a system identified by the firewall administrator as a critical strong point in the network's security; it usually hosts the application-level or circuit-level gateways. It runs a secure (trusted) version of its operating system; only the essential services (proxies for Telnet, DNS, FTP, SMTP, user authentication) are installed; it may demand extra authentication before allowing access to a proxy; each proxy supports only a subset of its application's commands, allows access only to specific hosts, logs all traffic, is a small program that can be checked for flaws, is independent of the other proxies, does no disk access beyond reading its configuration, and runs as an unprivileged user in a private directory.

\textbf{Screened host firewall, single-homed bastion} (a). The firewall consists of a packet-filtering router and a bastion host. The router is configured so that from the Internet only packets destined for the bastion host are allowed in, and from the internal network only packets from the bastion host are allowed out; the bastion host performs authentication and proxy functions. This is more secure than either component alone, because it combines packet-level and application-level filtering and an intruder must generally penetrate two separate systems; the router can also let some traffic, such as public web information, go directly to an information server. \emph{Weakness}: if the router is completely compromised, traffic can flow directly between the Internet and the private hosts.

\textbf{Screened host firewall, dual-homed bastion} (b). The bastion host has two network interfaces, one on the router's side and one on the internal network, so traffic between the Internet and the private hosts physically has to pass through the bastion host. This removes the weakness of (a): even a compromised router cannot bypass the bastion. An information server can still be placed on the outer segment for direct access.

\textbf{Screened subnet firewall} (c), the most secure configuration. Two packet-filtering routers are used, one between the bastion host and the Internet and one between the bastion host and the internal network, creating an isolated subnetwork, the \textbf{screened subnet} or \textbf{DMZ} (demilitarised zone), which holds the bastion host and public servers. Both the Internet and the internal network can reach the DMZ, but traffic across it is blocked. \emph{Advantages}: there are three levels of defence (outer router, bastion host, inner router); the outer router advertises only the DMZ to the Internet, so the internal network is invisible from outside; and the inner router advertises only the DMZ to the internal network, so inside systems cannot build direct routes to the Internet.

\textbf{Limitations of firewalls.} A firewall cannot protect against attacks that bypass it (an inside system with its own dial-out or mobile connection, a modem pool for travelling staff); it does not protect against internal threats (a disgruntled employee, or one who unwittingly helps an outside attacker); it cannot practically scan every file transferred for viruses, given the variety of formats; a laptop or USB drive infected outside can be carried in and attached inside; and it cannot inspect traffic that is encrypted end to end.

\subsection{Trusted systems: Bell--LaPadula and the reference monitor \hot\new}
\likely{``Explain the Bell--LaPadula model (no read up, no write down) and the reference monitor; how does a trusted system defeat a Trojan horse?'' (5--6 marks).}

\textbf{Problem.} Ordinary access control (an access matrix of subjects, objects and rights, stored per object as an access control list or per subject as capability tickets) lets the owner of a file pass its contents to anyone, and any program a user runs acts with all of the user's rights. Military and many commercial settings need a stronger guarantee: information classified at one level must never flow to a lower level, whatever users or programs do. Data and users are therefore given \textbf{security levels}, for example unclassified (U) $<$ confidential (C) $<$ secret (S) $<$ top secret (TS); a subject's level is its \textbf{clearance} and an object's level is its \textbf{classification}. A system that enforces such levels is a \textbf{multilevel secure} system.

\textbf{Bell--LaPadula model} (1973). A multilevel secure system must enforce two rules:
\begin{itemize}
  \item \textbf{No read up} (simple security property): a subject can only read an object of less or equal security level.
  \item \textbf{No write down} ($*$-property): a subject can only write into an object of greater or equal security level.
\end{itemize}
\textbf{Why both are needed.} No read up alone stops a secret-cleared user from reading top-secret data, but it does not stop information from leaking downwards: a secret-level process could read a secret file (allowed) and write its contents into an unclassified file, which any unclassified user may then read. The $*$-property closes that path: whatever a subject at level $L$ has read is at level $\le L$, and it can only write at level $\ge L$, so information can only flow upwards. Writing up is harmless for confidentiality (it is a blind append). Together the two rules guarantee that information never moves from a higher to a lower level.

\begin{worked}[: applying Bell--LaPadula]
\textbf{Q.} Levels are U $<$ C $<$ S $<$ TS. Subjects: General (TS), Officer (S), Clerk (C). Objects: War plan (TS), Report (S), Memo (C), Notice (U). Give the read (r) and write (w) operations allowed to each subject.

\textbf{A.} Read is allowed if subject level $\ge$ object level, write if subject level $\le$ object level; equal levels give both.

\textbf{Reference monitor.} The rules are enforced by a \textbf{reference monitor}, a controlling element in the hardware and operating system of a computer that regulates the access of subjects to objects on the basis of their security parameters. It consults the \textbf{security kernel database}, which lists the access privileges (security clearance) of each subject and the protection attributes (classification level) of each object, and it records important security events, such as detected violations and authorised changes to the kernel database, in an \textbf{audit file}.

The reference monitor must have three properties.
\begin{itemize}
  \item \textbf{Complete mediation}: the security rules are enforced on \emph{every} access, not only, for example, when a file is opened.
  \item \textbf{Isolation}: the reference monitor and its database are protected from unauthorised modification.
  \item \textbf{Verifiability}: the reference monitor's correctness must be provable, i.e.\ it must be possible to demonstrate mathematically that it enforces the security rules and provides complete mediation and isolation.
\end{itemize}
A system that can provide such verification is called a \textbf{trusted system}. These requirements are demanding: complete mediation in software would be too slow, so it needs hardware support; isolation requires that an attacker cannot change the monitor's logic or data; and formal verification is only feasible for a small, simple kernel. Evaluation criteria such as the US Orange Book (TCSEC, classes D to A1) and the international Common Criteria grade systems by how far these properties are achieved.

\textbf{Trojan horse defence.} Stallings' example shows why access control lists are not enough. Bob keeps a sensitive string in a file that only he may read and write. Alice, a legitimate but hostile user, installs a Trojan horse program and creates a private ``back-pocket'' file, giving herself read/write access and Bob write access to it. She persuades Bob to run her program, advertised as a useful utility. Running with Bob's rights, the program reads Bob's file and copies the string into the back-pocket file; both operations satisfy the ACLs, and Alice later reads her own file. In a trusted system, subjects get security levels at logon, say \emph{sensitive} for Bob's processes and files and \emph{public} for Alice's. When Bob runs the Trojan horse it acquires Bob's level, so it may read the sensitive string (no read up is satisfied), but its attempt to write into the public back-pocket file violates the $*$-property and is \textbf{refused by the reference monitor}, even though the ACL permits it. The security policy takes precedence over the discretionary ACL mechanism, and the leak is stopped.
